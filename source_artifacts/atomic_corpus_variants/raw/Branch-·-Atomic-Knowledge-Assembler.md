# Theoretical Specification

## Atomic Knowledge Assembler System

### 1. System designation

**Canonical name:** Atomic Knowledge Assembler  
**Abbreviation:** AKA  
**System class:** Retrieval, refinement, graph-semantic assembly, adaptive synthesis  
**Primary function:** Transform heterogeneous source material into minimally self-contained knowledge atoms, maintain them as a governed semantic-graph substrate, and assemble them on demand into outputs of variable scale, form, and purpose.

* * *

### 2. Design objective

The system is designed to replace static document-centric knowledge storage with an atom-centric substrate in which meaning is stored once, linked richly, and reassembled elastically. The theoretical premise is that knowledge should persist as the smallest independently interpretable unit, while documents become transient renderings rather than primary containers.

This yields five governing objectives.

| Objective | Description |
| --- | --- |
| Atomicity | Every stored unit must be independently interpretable without requiring hidden surrounding prose. |
| Reusability | The same atom may participate in many distinct assemblies without duplication. |
| Legibility | Every atom must remain inspectable, attributable, versioned, and auditable by both humans and machines. |
| Elasticity | The same substrate must support micro-summary, standard exposition, technical documentation, and long-form synthesis. |
| Updatability | Revision of one atom should propagate through future assemblies without manual rewriting of every derivative artifact. |

* * *

### 3. Core ontological commitments

The system rests on seven ontological assumptions.

First, **knowledge is compositional**. Complex understanding can be reconstructed from smaller semantically coherent units plus explicit relations.

Second, **documents are assemblies, not sources of truth**. The persistent truth-bearing objects are atoms, their relations, and their provenance.

Third, **meaning requires structure**. Vector similarity alone is insufficient; graph relations, role typing, and provenance must coexist with semantic embeddings.

Fourth, **recall is scale-dependent**. A system must distinguish foundational, supportive, contextual, and ornamental material.

Fifth, **truth requires provenance**. Every atom must maintain a tether to its originating evidence and transformation history.

Sixth, **knowledge changes through supersession, not silent mutation**. Old atoms are not erased conceptually; they are versioned, deprecated, or context-scoped.

Seventh, **assembly is governed generation**. Free-form generation is permitted only in connective tissue, framing, compression, or rhetorical shaping, not in unsupported factual invention.

* * *

### 4. System boundary

The system contains six major layers.

| Layer | Function |
| --- | --- |
| Ingestion Layer | Accepts raw sources such as notes, transcripts, documents, PDFs, datasets, and conversational logs. |
| Refinery Layer | Splits, extracts, compresses, deduplicates, validates, and atomizes source material. |
| Persistence Layer | Stores atoms, relations, provenance, embeddings, versions, and recipes. |
| Retrieval Layer | Selects atoms using hybrid graph, lexical, vector, temporal, and centrality constraints. |
| Assembly Layer | Orders atoms, fills structural gaps, applies templates, and renders outputs. |
| Governance Layer | Enforces schema, quality thresholds, lineage tracking, auditing, and policy rules. |

The system does **not** treat LLM free generation as the authoritative memory substrate. It treats generation as a controlled assembly and expression mechanism operating atop governed data.

* * *

### 5. Canonical atom definition

An atom is the smallest persistent unit of knowledge that satisfies all four conditions.

It must be **semantically self-contained**, **contextually typed**, **provenance-linked**, and **machine-addressable**.

A statement that depends on hidden neighboring context is not yet atomic. A sentence that is self-contained but untyped is still inadequate. A typed atom without provenance is unusable in high-trust contexts.

#### 5.1 Atom classes

| Atom class | Role |
| --- | --- |
| Axiom Atom | Foundational principle, invariant, or governing rule |
| Fact Atom | Verifiable declarative statement |
| Relation Atom | Explicit mapping between entities, states, or concepts |
| Procedure Atom | Instructional or operational step |
| Evidence Atom | Citation, quote, measurement, or observed datum |
| Context Atom | Scope condition, assumption, caveat, or environmental qualifier |
| Temporal Atom | Time-bound status, event, or supersession condition |
| Interpretation Atom | Synthesized inference explicitly marked as inferential |
| Recipe Atom | Saved assembly plan referencing ordered atom IDs |
| Policy Atom | Constraint governing retrieval, display, access, or use |

### 7. Persistence model

The theoretical storage model is hybrid by design.

#### 7.1 Graph substrate

The graph database stores entities, relations, abstraction hierarchies, contradiction edges, provenance edges, and dependency structure. This is the system’s logical skeleton.

#### 7.2 Vector substrate

The vector store supports semantic retrieval by contextual similarity, paraphrase matching, and latent concept proximity. This is the system’s associative field.

#### 7.3 Document substrate

Raw source artifacts remain stored intact, immutable, and addressable. This is the forensic archive.

#### 7.4 Relational or ledger substrate

Structured metadata, validation history, versioning, and operational telemetry are stored in conventional relational or event-sourced form. This is the administrative spine.

The theoretical architecture therefore rejects false exclusivity between graph and vector models. Graph handles logical explicitness; vector handles semantic elasticity.

* * *

### 8. Refinery pipeline specification

The refinery converts bulk material into governed atoms. It is not merely a chunking system. It is a semantic purification and structuring process.

#### 8.1 Phase I: Source registration

Each source enters with immutable identifiers, source type, origin, acquisition time, authorship metadata, and rights or access classification.

#### 8.2 Phase II: Mechanical segmentation

The source is segmented using structural markers such as headings, paragraphs, timestamps, speaker turns, list items, tables, or semantic boundaries.

#### 8.3 Phase III: Entity and relation extraction

Named entities, technical concepts, numerical values, dependencies, causal assertions, and explicit or implied relations are extracted.

#### 8.4 Phase IV: Atomic distillation

Each candidate segment is rewritten into one or more SIUVs: smallest independent units of value. The governing test is strict: if comprehension requires hidden adjacent text, the unit must be refined further.

#### 8.5 Phase V: Metadata crystallization

The system assigns class, semantic type, tags, embeddings, provenance spans, temporal scope, and candidate parent-child relations.

#### 8.6 Phase VI: Deduplication and merge arbitration

New candidates are compared against existing atoms using lexical similarity, vector similarity, structural similarity, provenance comparison, and contradiction logic.

#### 8.7 Phase VII: Validation

The system or reviewer verifies atomicity, clarity, truth conditions, and schema conformance.

#### 8.8 Phase VIII: Publication

The atom becomes queryable according to validation state and governance policy.

### 9. Atomicity test protocol

An atom is accepted only if it passes the following theoretical tests.

| Test | Question |
| --- | --- |
| Independence Test | Can this unit be understood without hidden local context? |
| Referential Test | Are core entities explicit or resolvable via linked identifiers? |
| Provenance Test | Can the origin be traced precisely enough for audit? |
| Scope Test | Is its temporal, contextual, or jurisdictional scope clear? |
| Non-Redundancy Test | Does it add value beyond existing atoms? |
| Role Test | Is its function in reasoning explicitly typed? |
| Assembly Test | Can it participate meaningfully in more than one possible output? |

Failure on any of these does not necessarily mean deletion; it may instead trigger decomposition, enrichment, or downgrade to a non-atomic intermediate artifact.

### 10. Retrieval logic

Retrieval is hybrid, weighted, and scale-aware.

The system computes a candidate set from multiple channels simultaneously: semantic proximity, graph neighborhood, direct entity match, taxonomic compatibility, time validity, validation state, and recipe prior.

A generic retrieval score may be modeled theoretically as:

$$
R(a, q) = w_s S(a,q) + w_g G(a,q) + w_t T(a,q) + w_c C(a) + w_u U(a) + w_v V(a) - w_d D(a,q)
$$

Where:

| Symbol | Meaning |
| --- | --- |
| $S(a,q)$ | Semantic similarity between atom and query |
| $G(a,q)$ | Graph relevance through linked entities and relations |
| $T(a,q)$ | Temporal relevance to requested context |
| $C(a)$ | Centrality or foundational importance |
| $U(a)$ | Utility based on prior assembly success |
| $V(a)$ | Validation and trust weighting |
| $D(a,q)$ | Distance penalty, contradiction penalty, or stale-data penalty |

### 11. Fractal recall and resolution scaling

The system must support elastic zoom.

#### 11.1 Resolution bands

| Resolution band | Function |
| --- | --- |
| Micro | Core claim only; highest-density atoms |
| Compact | Core claim plus essential support |
| Standard | Balanced explanatory output |
| Extended | Full operational or analytical treatment |
| Deep | Includes edge cases, evidence lattice, contradiction handling, and provenance visibility |

#### 11.2 Fractal expansion rule

Every atom may be linked upward to more abstract parent structures and downward to finer-grained children. This permits recall at the level of principle, subsystem, implementation detail, or evidence trace.

The same topic can therefore be rendered as a one-line summary, a briefing memo, a technical specification, or an annotated white paper without changing the substrate—only the assembly depth changes.

### 12. Assembly logic layer

Assembly is the act of selecting, ordering, shaping, and connecting atoms into a coherent output artifact.

#### 12.1 Assembly stages

| Stage | Description |
| --- | --- |
| Scope resolution | Infer requested depth, form, audience, and trust requirement |
| Candidate acquisition | Retrieve atom pool using hybrid scoring |
| Structural selection | Group atoms into a template-compatible outline |
| Gap analysis | Detect missing premises, transitions, or evidentiary holes |
| Connective generation | Generate only the minimal rhetorical tissue needed |
| Coherence pass | Ensure sequence, terminology consistency, and causal clarity |
| Provenance rendering | Expose citations or evidence markers as required |
| Recipe capture | Save atom order and template parameters as reusable recipe |

#### 12.2 Template molds

A template does not change the atoms’ truth; it changes their rhetorical arrangement. A briefing template prioritizes action relevance. A technical manual prioritizes procedures and dependencies. An academic note prioritizes citations, definitions, and competing interpretations.

Templates therefore function as **assembly grammars** rather than content sources.

### 13. Recipe persistence

The system should preserve not merely output text but **assembly recipes**.

A recipe stores the ordered atom IDs, template ID, resolution band, audience mode, and connective rules used in a successful assembly. This permits regeneration after underlying atom updates and supports derivative consistency across formats.

A recipe is therefore a second-order knowledge object: a reusable plan for how truth-bearing atoms are combined under a given communicative objective.

### 14. Weighting algorithm specification

The brainstorm’s weighting logic is sound, but it should be formalized into a composite system.

#### 14.1 Centrality

Atoms with many dependencies or many downstream uses receive higher inclusion priority in constrained outputs.

#### 14.2 Semantic proximity

Atoms whose embeddings align closely with the query or selected entities receive stronger topical relevance scores.

#### 14.3 Utility decay and promotion

Frequently useful atoms rise in rank; obsolete or superseded atoms decay unless the query explicitly asks for historical state.

#### 14.4 Functional role weighting

Axioms and policies receive near-mandatory inclusion when structurally relevant. Evidence atoms scale in later as resolution increases. Anecdotal atoms remain low-priority except in narrative or illustrative modes.

#### 14.5 Information gain

Atoms that contribute maximal entropy reduction per token are preferred under tight token budgets.

A composite inclusion score may be expressed as:

$$
I(a) = \alpha C(a) + \beta S(a,q) + \gamma U(a) + \delta F(a) + \epsilon E(a) + \zeta T(a) 
$$

Where $F(a)$ is functional-role weighting and $E(a)$ is information gain.

### 15. Provenance and truth model

The system must be able to answer not only “What is the claim?” but also “Why should this claim be trusted?” and “What exactly produced it?”

Each atom therefore requires three lineage layers.

| Layer | Question answered |
| --- | --- |
| Source provenance | From what original artifact did this arise? |
| Transformation provenance | What extraction, compression, merge, or review operations produced this atom? |
| Assembly provenance | In what outputs has this atom been used, with what neighboring atoms and templates? |

This tri-layer provenance model is critical if the system is used in academic, legal, scientific, or operational domains.

### 16. Governance and version control

A serious system of this type requires governance equal in rigor to software change control.

#### 16.1 Versioning rules

Atoms are immutable in principle. Corrections create successor atoms with explicit supersession edges. Silent overwrite is disallowed for validated material.

#### 16.2 Validation states

Recommended states are `draft`, `machine-distilled`, `human-reviewed`, `verified`, `deprecated`, and `disputed`.

#### 16.3 Contradiction handling

Contradictory atoms should not be collapsed prematurely. They should coexist under contradiction edges with scope conditions, evidentiary priority, and jurisdiction or temporal qualifiers.

#### 16.4 Access control

Some atoms may be public, some internal, some privileged, and some derivatively sensitive. Access policy attaches at both source and atom level.

GraphQL is appropriate when clients require precise structured traversals. REST can work for stable operational endpoints. Event streams are preferred for change propagation and recipe invalidation notifications.

The key theoretical requirement is not the protocol brand but the existence of a stable, explicit contract for addressing atoms, relations, recipes, and provenance.

# Should the code-centric atomic feature be built in unison or separately?

The correct answer is **both**, but at different layers.

It should be built **in unison conceptually** and **separately operationally**.

The shared layer should include the identity model, provenance model, graph relation model, supersession rules, retrieval API, recipe format, temporal weighting, contradiction handling, and assembly semantics. This allows a business-rule text atom to point to the code atom that implements it, and lets a policy change trigger impact analysis across code and documentation. This is precisely where graph relations are strong: representing entities, relationships, and dependencies explicitly.   [Graph Database & Analytics](https://neo4j.com/docs/getting-started/graph-database/?utm_source=chatgpt.com)  

The separate layer should include the refinery and persistence behavior for code. Code is not just another prose source. It needs AST-aware parsing, dependency extraction, symbol resolution, runtime metadata, complexity metrics, and more rigid validation. Tree-sitter is built for concrete syntax trees and efficient incremental updates, which makes it a sensible parser layer for a code refinery. For storage, content-addressed immutability is a good fit for code atoms and build artifacts, as shown by LLVM CAS and by IPFS/IPLD’s use of CIDs and Merkle DAGs for immutable linked objects.   [Tree-sitter](https://tree-sitter.github.io/?utm_source=chatgpt.com)  

So the design rule is:

**One ontology, two refineries.  
One graph of truth, separate atomizers.  
One retrieval contract, distinct storage optimizations.**

# What I recommend specifically

I recommend a **phased hybrid architecture**.

Phase 1 should define a unified atom schema that covers both prose atoms and code atoms, but with subtype-specific fields. For example, code atoms would add AST node type, signature, imports, runtime, dependency edges, side-effect profile, test coverage pointer, and content hash. Text atoms would retain source span, semantic type, evidentiary role, and temporal scope. Both would share IDs, provenance, graph edges, supersession, validation state, and recipe participation.

Phase 2 should implement **text/document atoms first** and **code atoms second**, but the schema must be designed for both from day one. This avoids the common mistake where the prose system becomes impossible to extend into executable logic later.

Phase 3 should use **local or internal content-addressable storage**, not full IPFS as a first deployment. IPFS and IPLD are valuable conceptual references for CIDs, Merkle DAGs, and linkable immutable objects, but for an internal system the distributed network layer is usually unnecessary overhead at the start. A Git-like or LLVM-CAS-like internal CAS is more appropriate initially; GraphQL can sit above it as a typed retrieval and assembly contract.   [IPFS Docs](https://docs.ipfs.tech/concepts/content-addressing/?utm_source=chatgpt.com)  

Phase 4 should add cross-domain bridges: policy atom → requirement atom → test atom → function atom → build artifact atom → deployment state atom.

# Where I would be cautious

I would **not** start with a fully versionless ideology in the literal sense. Content-addressable systems are immutable and excellent for exact states, but humans still need understandable revision semantics. IPNS exists precisely because immutable CIDs need a mutable naming layer above them. In practice, your system will want both immutable objects and stable human-facing names or portals.   [IPFS Docs](https://docs.ipfs.tech/concepts/ipns/?utm_source=chatgpt.com)  

I would also **not** start with “pure function atomization” as the only code model. It works for many functions, but real code contains stateful procedures, I/O boundaries, configuration surfaces, class methods, declarative infrastructure, tests, migrations, UI components, and glue code that are not clean pure functions. AST-based extraction should therefore identify several code atom types, not just one.

I would also avoid assuming that vector retrieval alone can recover code intent. For code, symbol graphs, call graphs, import graphs, AST features, and test relations often matter more than raw embedding proximity. That is another reason the code layer should be a specialized subsystem, not merely “text atomization plus embeddings.”

My ranked recommendation is:

**First:** formal system architecture specification.  
**Second:** unit-economics / complexity simulation model.  
**Third:** pilot-scale operational playbook.

For the added feature, I recommend:

**Design it now in the same architecture. Implement it as a separate refinery and storage path.**

That gives you a unified knowledge OS rather than two incompatible systems, while still respecting the fact that code is structurally different from prose.

## Q: 
Simultaneously during the building and maintenance of this new version of the knowledge base, a parallel system elsewhere will be generating linguistic analysis. The goal would be to bring ideas and results into the new place. And is that, that's something we need to design for, what would that look like.

## A: 
# Yes — design for it now

That parallel linguistic-analysis system should not be treated as an external convenience. It should be treated as a **first-class upstream producer** in the overall architecture.

If you do not design for it now, you will later end up with one of two bad outcomes:

First, the linguistic system will dump opaque reports into the knowledge base as dead documents, which recreates the very monolith problem you are trying to escape.

Second, you will over-couple the new knowledge base to the internal assumptions of the linguistic system, which will make both harder to evolve.

The correct design is a **federated atomic intake model**:

**external analysis system produces structured findings → translation layer converts them into governed atoms → new knowledge base stores them as linked, typed, provenance-rich objects**

So the answer is yes: this absolutely needs to be designed for, and it should be designed as a formal integration lane, not an ad hoc import feature.

* * *

# What it should look like conceptually

You now have three distinct domains:

| Domain | What it contains | What it is good at |
| --- | --- | --- |
| Source domain | raw conversations, documents, notes, code, media-derived text | primary evidence |
| Linguistic-analysis domain | token patterns, syntax, rhetoric, discourse, semantic drift, ontology extraction, motif recurrence, style signatures | interpretation and structural analysis |
| Knowledge-base domain | durable atoms, relations, recipes, provenance, assembly, cross-domain retrieval | long-term governed memory |

The linguistic-analysis system should therefore be treated neither as raw evidence nor as final truth.

It is a **derivative analytical instrument**.

That means its outputs should enter the new system in a distinct ontological class, somewhere between evidence and interpretation.

* * *

# The key design principle

Do **not** import linguistic-analysis outputs as plain text reports.

Instead, import them as **structured analytical products** that can be decomposed into atomic findings.

The integration model should be:

Plain text

```
Raw source   ↓Parallel linguistic-analysis system   ↓Analytical export package   ↓Translation / normalization layer   ↓Knowledge atoms + relation atoms + provenance atoms + confidence metadata   ↓Assembly-ready knowledge substrate
```

The crucial piece is the **translation / normalization layer**. That is the membrane between systems.

Without that membrane, the knowledge base gets polluted with foreign assumptions, foreign schemas, and ungoverned interpretation objects.

* * *

# What kinds of things the linguistic system would produce

The external linguistic-analysis system may generate many classes of output. These should be anticipated now.

A non-exhaustive analytical ontology would include the following families:

| Output family | Example |
| --- | --- |
| Lexical findings | recurrent word clusters, terminology emergence, rare vocabulary spikes |
| Syntactic findings | sentence-complexity trends, clause chaining, imperative density |
| Semantic findings | concept neighborhoods, synonym drift, semantic compression, domain mapping |
| Discourse findings | topic transitions, framing shifts, narrative pivots, self-reference density |
| Pragmatic findings | intent patterns, directive vs exploratory tone, uncertainty markers |
| Rhetorical findings | metaphor patterns, contrast structures, repetition motifs, persuasive framing |
| Ontological findings | entity extraction, concept hierarchies, category proposals, taxonomy suggestions |
| Temporal findings | language drift over time, concept evolution, recurring sequences |
| Comparative findings | differences across projects, time windows, authors, systems, or modalities |
| Signature findings | stylistic fingerprints, preferred structures, recurrent symbolic patterns |

These outputs should not all be treated the same way. Some are more like evidence, some more like interpretation, some more like proposed ontology, and some more like diagnostics.

So the knowledge base must distinguish them formally.

* * *

# What new atom types you need

To support this, I would extend the v2 ontology with a specific analysis lane.

At minimum, add these atom classes:

| Atom type | Purpose |
| --- | --- |
| `AnalysisAtom` | a normalized analytical finding |
| `ObservationAtom` | lower-level pattern directly observed from a corpus |
| `InterpretationAtom` | an inferential conclusion derived from observations |
| `MetricAtom` | numeric output from the linguistic system |
| `TaxonomyProposalAtom` | proposed category, cluster, or concept grouping |
| `SignatureAtom` | persistent stylistic or structural pattern |
| `DriftAtom` | a change-over-time pattern in language or meaning |
| `AnalysisRunAtom` | metadata about one execution of the external analysis pipeline |

These should be distinct from ordinary `TextAtom`, `CodeAtom`, and `EvidenceAtom`.

That matters because a sentence in a source conversation and a sentence produced by a linguistic-analysis engine are not the same kind of object.

One is source evidence. The other is analytical output about that source.

# Provenance model for the parallel system

This is where most systems fail.

You need two-layer provenance at minimum, ideally three-layer provenance.

## Layer 1: source provenance

What raw corpus was analyzed?

For example:

conversation IDs  
document IDs  
time windows  
author scopes  
project scopes  
code scopes  
selection filters

## Layer 2: analysis provenance

What exact analytical run produced the result?

For example:

analysis engine name  
version  
prompt or model config  
algorithm class  
parameters  
dictionary / ontology versions  
timestamp  
confidence method

## Layer 3: transformation provenance

How was the external result translated into the knowledge base?

For example:

normalization rules  
schema version  
import job ID  
conflict-resolution logic  
deduplication outcome

This gives you traceability from final stored finding back to both the raw source and the analytical mechanism that produced it.

Without this, analytical outputs become untrustworthy very quickly.

# How the integration should work architecturally

The cleanest model is a **publish-normalize-ingest** pattern.

## 1. Publish

The linguistic-analysis system should export structured result bundles, not prose-only summaries.

Those bundles should be machine-readable and stable.

The export object should contain:

run metadata  
corpus scope  
findings  
metrics  
links back to source spans  
confidence values  
proposed relations  
optional embeddings  
optional cluster identifiers

## 2. Normalize

A dedicated integration service reads the export and maps it to the knowledge-base ontology.

This service should:

resolve source references  
convert external identifiers to internal identifiers  
separate observations from interpretations  
assign atom classes  
add validation state  
merge duplicates  
record provenance  
generate relation edges

## 3. Ingest

The normalized output is stored as first-class atoms and linked into the broader graph.

At this stage the system can connect:

analysis findings to source evidence  
analysis findings to text atoms  
analysis findings to code atoms  
analysis findings to prior analyses  
analysis findings to recipes and assemblies

* * *

# The data contract you should define now

You need an explicit contract between the external linguistic system and the new knowledge base.

This does not need to be technologically fancy at first, but it must be semantically strict.

The external system should never “just send a paragraph.”

It should send something like a structured analytical envelope with fields equivalent to:

| Field | Meaning |
| --- | --- |
| `analysis_run_id` | unique ID for one run |
| `analysis_type` | discourse, semantic drift, syntax, rhetoric, etc. |
| `source_scope` | what corpus or slice was analyzed |
| `finding_id` | stable ID for each exported finding |
| `finding_kind` | observation, interpretation, metric, taxonomy proposal, signature |
| `finding_text` | normalized human-readable statement |
| `evidence_refs` | source spans or source atom IDs |
| `confidence` | numeric or categorical confidence |
| `method` | algorithm/model/process used |
| `timestamp` | when produced |
| `supersedes` | prior finding if applicable |
| `tags` | ontology or domain tags |
| `relations` | explicit suggested edges to internal objects |

That contract is what allows the two systems to evolve independently.

* * *

# How to prevent contamination of the core knowledge base

You do not want every analytical output immediately treated as stable truth.

So you need a **trust gradient**.

I recommend the following validation states for imported analysis objects:

| State | Meaning |
| --- | --- |
| `imported` | accepted from external system, not yet reviewed |
| `machine-derived` | known to be analysis-generated |
| `reviewed` | checked by human or trusted adjudicator |
| `accepted` | allowed in normal assembly for standard outputs |
| `experimental` | visible only in exploratory or research contexts |
| `disputed` | challenged or contradicted |
| `deprecated` | superseded by newer or better analysis |

This keeps the analytical lane useful without letting it silently rewrite the ontology.

* * *

# The most important relation types

To make the parallel system genuinely useful, define these edge types from the start.

| Relation | Meaning |
| --- | --- |
| `analyzes` | analysis object analyzes a source or atom |
| `derived_from` | finding comes from a source span or atom set |
| `supports` | finding strengthens another atom or interpretation |
| `contradicts` | finding conflicts with another atom or interpretation |
| `proposes_taxonomy_for` | analysis proposes ontology over a corpus |
| `detects_drift_in` | identifies change over time in an entity, topic, or style |
| `characterizes` | gives a structural description of an entity/corpus/project |
| `maps_to` | aligns an external analysis label to an internal concept |
| `requires_review_of` | flags atom or code object for re-evaluation |
| `is_superseded_by` | analysis result replaced by newer run |

These edges are what convert “interesting reports” into operational knowledge.

# How this becomes practically useful

Once integrated correctly, the linguistic-analysis system can do more than annotate language. It becomes a trigger system for knowledge maintenance.

Examples:

A semantic-drift finding can indicate that a concept has changed meaning across a project over six months, which should trigger taxonomy review.

A rhetoric-pattern finding can reveal that a set of memos consistently mixes instruction and speculation, which should trigger atom reclassification.

A business-rule language shift can be linked to code atoms implementing that rule, which should trigger impact analysis.

A motif recurrence analysis can identify latent conceptual clusters across notes, which can seed new ontology branches.

A discourse-structure analysis can produce reusable recipes for assembling future reports in the style that best matches the corpus.

That is when the external analytical system stops being “another report generator” and becomes a genuine co-processor for the knowledge OS.

* * *

# Whether this should be synchronous or asynchronous

Architecturally, this should usually be **asynchronous** at the system level, even though conceptually it is parallel.

The linguistic system should run on its own cadence and publish result bundles.

The knowledge base should ingest those bundles through a controlled pipeline.

That keeps the systems decoupled and resilient.

However, the knowledge base should also support **on-demand federation**, meaning an assembly or query can ask:

“show me source atoms plus the latest accepted linguistic analyses relevant to this topic”

So the systems are operationally decoupled but logically composable.

* * *

# Recommended structural pattern

The cleanest pattern is this:

## Core substrate

Stores source atoms, code atoms, evidence atoms, recipes, and accepted analysis atoms.

## External analysis exchange layer

Receives export bundles from the linguistic-analysis system.

## Normalization membrane

Maps foreign results into local ontology and trust states.

## Analytical graph lane

Stores imported analysis runs and findings as a distinct subgraph.

## Assembly policy layer

Determines when analytical findings are included in normal outputs, exploratory outputs, or deep-research outputs.

That gives you a separation between **memory**, **analysis**, and **rendering**.
